## [2026-09-14] higher-order-factory（高阶工厂）

**来源**：测试重构讨论
**核心**：当 helper 只服务"最简场景"时，用回调注入"特定部分" —— 通用 How 由框架管，特定 What 由用户注入。
**可能类型**：模式
**关联**：[[S31]] [[patterns/what-how-are-projections]]
**状态**：pending

### 补充（2026-09-14）：候选池机制

A19 的 L5（落地）**不是"每轮立刻沉淀"** —— 是"**每轮记录候选 + 达阈值后归并沉淀**"。

**候选池位置**：`working-memory/candidate-queue.md`
**触发条件**：队列 ≥ 5 项 / 任一 ≥ 7 天 / 3 个相关 / 用户要求
**沉淀动作**：归并相似 → 1-3 个条目 → 更新状态

### L1 补充：扫描深度按任务决定

**不是固定轮次** —— 按以下判据：

| 任务类型 | 深度 |
| :--- | :--- |
| **单点修复** | 当前文件 + 上下文 3 轮 |
| **局部重构** | 相关模块 + 上下文 10 轮 |
| **跨文件重构** | 所有相关条目 + 上下文 20-30 轮 |
| **架构决策** | 全项目 + 所有相关讨论 |

**判断方法**：
1. 本次改动会触及几层？
2. 会触及几条已有约定？
3. 未来会被引用吗？

**≥ 2 个"是"** → 取最大深度。

"scripts 分档 + 长期脚本 TS 化" —— 进候选队列，不立刻沉淀。

### L4 补充：递归轮数按任务决定

**不是固定轮次** —— 按"每轮是否产出新东西"决定。

| 任务类型 | 递归轮数 |
| :--- | :--- |
| **单点分析**（一个具体问题）| 1-2 轮 |
| **跨文件分析** | 2-3 轮 |
| **架构决策** | 3-5 轮 |

**收敛判据**（每一轮结束问）：

1. **本轮是否发现"上一轮没看到的"？**
    - 有 → 继续
    - 没有 → 收敛
2. **本轮的结论和上一轮是否等价？**
    - 等价 → 收敛
3. **本轮的分析是否进入"元层面"（方法论）？**
    - 是 → 收敛

**"为运行而运行"是反模式** —— 递归的目标是"更深"，不是"更多"。

你说的"在不违反标准的情况下能派生就派生" —— 我落成一条通用原则：

"派生优于复制" —— 即使代价是"多一次 import"。
例外：当"派生"违反其他标准时（如"脚本必须独立运行"）—— 才允许硬编码 + 注释。
