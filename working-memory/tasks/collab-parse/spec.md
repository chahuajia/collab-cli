**作者**：codex（AI 提议）

## 上下文

`collab apply` 打通了"bundle.json → 工作区"。**但 bundle.json 从哪来？**

A17 规定对话式 AI 的多文件输出要用文本协议：

```text
===== FILE: <相对路径> =====
<完整内容>
===== END FILE =====
```

现状：AI 输出这段文本 → 用户复制到文件 → **然后没有工具把它变成 bundle.json**。
这个缺口此前由一次性脚本填（`scripts/extract-bundle.mjs`、`split-collab.mjs`、
`recover.mjs`），它们都用 `process.cwd()` 定位工作区，且各写各的切分逻辑。

一句话：**`apply` 是落盘通道，`parse` 是进料口。少了进料口，人还是要手工切。**

## 目标

把 A17 文本切成 `bundle.json`，**并且只在完全切分成功时产出**。

| # | 目标 | 可观察结果 |
| :--- | :--- | :--- |
| G1 | 切分 | N 个块 → `files` 有 N 项，`content` 与原文**逐字节一致** |
| G2 | 可信 | 每个文件带自洽的 `sha256`（`apply` 会验它） |
| G3 | 拒绝坏输入 | 块外有内容 / 块未闭合 / 空块 / 路径重复 → 整体失败，不产文件 |
| G4 | 与 `apply` 直连 | `parse` 的产物**无需手改**即可被 `apply` 接受 |

## 非目标

- ❌ 剪贴板读取（浏览器/系统集成）—— 用户先存成 `.txt` 即可；等真实痛感。
- ❌ MsgPack / `pack` / `dump-bundle`（交接清单 P0-2/P0-3）—— 先证 JSON 够用。
- ❌ 三方合并、冲突自动解决。
- ❌ 自动 `commit` / `push`（[[A7]]：AI 不 commit、不 push）。

## 接口（草案）

```bash
collab parse <source.txt|-> [--out <path>] [--stdout] [--json]
```

| 选项 | 行为 |
| :--- | :--- |
| `<source.txt>` | A17 文本文件；`-` 表示读 stdin |
| `--out <path>` | 输出路径，默认 `bundle.json`（相对 cwd） |
| `--stdout` | 打到 stdout，不写文件（管道友好） |
| `--json` | 与 `--stdout` 合并为"输出 JSON"？（**待拍板 D4**） |

## 行为规格

### 1. 切分

以 `===== FILE: <path> =====` 开始、`===== END FILE =====` 结束。
块内容为两标记之间的**全部文本**（保留换行；不 trim 尾部空行）。

### 2. 拒绝（全有或全无，与 `apply` 同构）

| 检查 | 失败时 |
| :--- | :--- |
| 第一个标记之前存在**非空白**内容 | 拒绝（多半是 AI 的开场白被一起粘进来） |
| 存在未闭合的块 | 拒绝 |
| 块内容为空或纯空白 | 拒绝（多半是粘贴截断 —— 这正是 2026-09-15 事故的形态） |
| 同一个 `path` 出现两次 | 拒绝（不知道哪个是最终版） |
| `path` 为空 | 拒绝 |
| 一个块都没有 | 拒绝 |

> 与 `apply` 的分工：`parse` 管**切分正确**，`apply` 管**路径安全 + 冲突**。
> `parse` 不重复实现白名单/`..` 检查 —— 预检只有一份（见 `apply` spec 的反面）。

### 3. 产出

```json
{
  "version": 1,
  "generated_at": "<now, ISO8601>",
  "generated_by": "collab parse",
  "base_commit": null,
  "files": [
    { "path": "...", "action": "create|replace", "content": "...",
      "sha256": "...", "base_sha256": null }
  ]
}
```

## 验收（先写测试，再写实现）

| # | 场景 | 期望 |
| :--- | :--- | :--- |
| P1 | 2 个合法块 | `bundle.json` 有 2 项；`content` 与原文一致；`sha256` 自洽 |
| P2 | 块前有开场白 | 拒绝，不产出 |
| P3 | 缺 `===== END FILE =====` | 拒绝 |
| P4 | 空块 | 拒绝 |
| P5 | 同一 path 两次 | 拒绝 |
| P6 | 没有块 | 拒绝 |
| P7 | `--stdout` | 打印 JSON，不写文件 |
| P8 | 从 stdin（`-`）读 | 与文件输入等效 |
| P9 | 端到端 | `parse` 的产物 `apply` 直接吃下，exit 0，文件内容与原文一致 |
| P10 | `path` 带 `COLLABORATION/` 前缀 | 原样写进 bundle；`apply` 负责规范化（E6） |

## 反面

- 不要改 A17 协议去迁就实现 —— 协议是给 AI 的，工具应当适配它。
- 不要在 `parse` 里做路径白名单 —— 那是 `apply` 的预检，重复就会漂移。
- 不要把切分失败"尽力而为"地修复（猜边界）—— 猜错会把错内容写进知识库。
- 不要默认写进知识库目录 —— 产出是 `bundle.json`，落盘是下一步。
- 不要吞掉"块外有内容"这个信号 —— 它常常说明用户粘贴范围错了。

## 未决问题（需要人拍板）

### D1. `action` 怎么定？（最关键）

A17 文本里**没有** action 字段。三条路：

| 选项 | 说明 | 代价 |
| :--- | :--- | :--- |
| **A. 全 `create`** | 最简单 | 目标已存在时 `apply` 必拒；修一条要手工改 JSON |
| **B. 按工作区现状推断** ⭐ | 文件不存在 → `create`；已存在 → `replace` + `base_sha256` = 当前哈希 | `parse` 需要读工作区（要定位 COLLABORATION 根）；可能"猜错用户意图" |
| **C. 扩 A17** | 文本里声明 action | 改协议（走 [[W7]]），且 AI 未必知道现状 |

**推荐 B**：AI 产出的批次里，新建与修订本来就混在一起；让工具去读现状比让 AI 猜更准。
但 B 会让 `parse` 从"纯切分"变成"需要工作区上下文"—— 这是它的主要缺点。

### D2. 输入来源要不要支持 stdin？

**推荐支持**（`-`）。理由：管道是"复制 → 落盘"最短路径；不做也就多一个临时文件。

### D3. 默认输出到哪？

**推荐**：默认写 `bundle.json`（当前目录），`--out` 可覆盖。
不推荐默认打到 stdout —— 用户下一步要 `apply <file>`，文件更直接。

### D4. `--json` 与 `--stdout` 是两个选项还是一个？

**推荐合并为一个** `--stdout`（输出**就是** JSON）。另设 `--json` 只会造成两种 JSON 模式。

### D5. A17 文档里的标记疑似有笔误，解析要多宽容？

A17 原文两处结束标记不一致（一处 `===== END FILE =====`，另一处 `===== END FILE ====`，少一个 `=`）。

| 选项 | 说明 |
| :--- | :--- |
| **A. 严格**（必须恰好 5 个 `=`） | 简单；但真实 AI 输出会有出入，用户要手工修 |
| **B. 宽容**（`^=+\s*END FILE\s*=+$`）⭐ | 容错；代价是"看起来像标记的正文"可能被误判 |

**推荐 B + 同时修 A17 文档的笔误**。

### D6. `scripts/extract-bundle.mjs` / `split-collab.mjs` / `recover.mjs` 的处置

它们与 `parse` 功能重叠，且都用 `process.cwd()` 定位工作区（collaboration 遗留 §"迁移后的脚本假设 cwd"）。

| 选项 | 说明 |
| :--- | :--- |
| **A. `parse` 落地后删除这些脚本** ⭐ | 消灭第二份真相源（沿用 2026-09-16 决策：工具只留一处） |
| **B. 保留，加 `--dir`** | 兼容旧习惯；但多一份要维护的规则 |

**推荐 A**，但要先确认它们没有 `parse` 不覆盖的能力（如 `recover.mjs` 的恢复逻辑）。
